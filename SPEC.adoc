:doctitle: cl-adoc language specification

= cl-adoc v1

This document defines the subset of the AsciiDoc language that cl-adoc
parses and renders. It is versioned independently of the cl-adoc library
itself. Additions live in v2, v3, and so on — this file describes v1 only.

Status markers used below:

* unmarked — fully supported
* *(!)* — partially supported
* *(X)* — deliberately not supported, with reasoning
* *(?)* — planned, not yet implemented

== Document Header

* Document title (single-line `=` form)
* `:key: value` attribute entries
* *(?)* Author line, single author
* *(?)* Attribute references elsewhere in the document (`{key}`)
* *(X)* Multi-author lines. Rationale: rare for the kind of writing this
  targets; revisit if the collective grows past a few contributors sharing
  a byline.

== Sections

* Heading levels via `=` through `====` (title through level 3)
* Autogenerated section IDs, used for anchors and the table of contents
* *(X)* Custom ID / reference text assignment (`[[custom-id]]`). Rationale:
  not needed until cross-references exist; add alongside those.

== Paragraphs and Text Formatting

* Paragraphs
* Bold (`*text*`), italic (`_text_`), monospace (`` `text` ``)
* A delimiter only opens a span at a word boundary, so `snake_case_name`
  and arithmetic like `2 * 3 * 4` are left alone
* Monospace content is literal — no formatting is recognized inside a code
  span, so `` `foo_bar_baz` `` keeps its underscores. This departs from
  Asciidoctor, which does substitute inside backticks. Rationale: a code
  span exists to show text exactly as it was written, and re-reading its
  contents as markup is the specific bug this parser was built to avoid.
* *(?)* Hard line breaks
* *(?)* Subscript and superscript

== Lists

* Unordered lists, single marker: `*`
* Ordered lists, single marker: `.`
* Checklists (`[ ]`, `[x]`, `[X]`) — note: literal bracket text at the start
  of a list item must be escaped (`\[ ]`), since this exact position is
  where checklist syntax is recognized.
* An item continues onto following lines until the next item or the next
  block, so long items may be soft-wrapped
* A marker is only a marker in the first column, followed by a space. That
  is what keeps a line opening with `*bold*` a paragraph, and it follows
  from nesting being excluded — an indented marker would have nowhere to go.
* *(X)* Hyphen-marker unordered lists (`-`). Rationale: ambiguous once
  quoted paragraphs or em dashes enter the picture — a line starting with
  `-` could be a new list item or a continuation of prose. One marker, no
  ambiguity.
* *(X)* Nested lists (more than one level). Rationale: not yet needed;
  single level covers everything written so far. Revisit if a post
  genuinely needs it.

== Links and Images

* Autolinks for bare `http://` and `https://` URLs. A URL stops before
  trailing sentence punctuation, so a link ending a sentence does not
  swallow the period; punctuation with more URL after it is kept.
* Link macro: `link:url[text]`, where `link:url[]` displays the target
* Block image macro: `image::path[alt text]`, alone on its line — the
  bracket has to close the line, or it is ordinary prose
* Inline images: `image:path[alt text]`
* Attribute lists are positional, and end at the first `]`. There is no way
  to escape a closing bracket inside one. Rationale: a half-working escape
  nobody documented is worse than a limit that is written down.
* *(?)* Autolinks for other schemes, `mailto:` most of all
* *(?)* Named attributes, and image width and height
* *(X)* Audio and video macros. Rationale: no current use case; the
  two-lane writing/hobby content this targets is text- and image-first.

== Admonitions

* `NOTE:`, `TIP:`, `WARNING:`, `IMPORTANT:`, `CAUTION:`, single-paragraph
  form only
* The label is matched exactly, including the space after the colon, so a
  paragraph opening `NOTES: ` or `Note: ` is prose
* *(?)* Block admonitions (`[NOTE]` above a delimited block), which is the
  form that carries more than one paragraph

== Blocks

* Delimited listing blocks (`----`)
* Source blocks with a language attribute (`[source,lang]`)
* *(?)* Delimited STEM/math blocks (`++++`) and inline `stem:[...]`
* Blockquotes (`> `, line-prefixed form). A bare `>` separates one paragraph
  of a quotation from the next; the space after the marker is required, so a
  line opening `>text` is prose.
* *(?)* Quotation attribution (`[quote, author, source]`)
* *(X)* Sidebars, example blocks, open blocks. Rationale: no content has
  needed them yet; straightforward to add when something does.
* *(X)* Callouts in source blocks. Rationale: requires per-language
  comment-syntax awareness to implement well; a lot of complexity for a
  feature that's easy to fake with a numbered list under the block
  instead.

== Tables

* *(?)* Basic `|===` delimited tables, pipe-separated cells
* *(?)* First row as header
* *(X)* Nested tables. Rationale: nested tables are close to always the
  wrong way to present information; if the data needs that, it needs a
  different shape, not a table.
* *(X)* Column/cell format specifiers (widths, spans, alignment).
  Rationale: not yet needed; add when a real table needs one.

== Table of Contents

* *(?)* Automatic TOC generation from section headings

== Includes

* *(?)* Single-file include directive
* *(X)* Include by tagged region, include by line range, include by URI.
  Rationale: real complexity, no current need, and the URI form adds a
  network dependency to what should be a deterministic build.

== Comments

* *(?)* Line comments (`//`)

== Substitutions

* Special character escaping, both in source/listing blocks and in
  ordinary paragraph text
* Backslash escapes for inline formatting delimiters
* *(?)* Passthrough blocks (`++++`), shared with STEM
* *(X)* Custom substitution ordering per block. Rationale: an escape
  hatch for a problem this document set hasn't hit yet.
