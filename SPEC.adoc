= cl-adoc v2

This document defines the AsciiDoc subset that cl-adoc parses and renders.

SPEC.adoc and the cl-adoc library use separate versions.

This file describes v2. Version 2 is v1 plus description lists. No other
language rules changed.

Description lists were added because the first real consumer needed them. The
anchor specification uses description lists throughout. anchor is also meant to
render its own specification.

The subset grows only when a real document set needs a construct.

Status markers:

* unmarked — fully supported
* *(!)* — partially supported
* *(X)* — not supported, with reason
* *(?)* — planned, not yet implemented

== Document Header

* Document title, written with the single-line `=` form
* `:key: value` attribute entries
* *(?)* Author line, single author
* *(?)* Attribute references elsewhere in the document, written `{key}`
* *(X)* Multi-author lines.
+
Reason: They are rare for the writing this parser targets. Revisit this if a
document needs more than a few contributors on one byline.

== Sections

* Heading levels from `=` through `====`
+
These are the document title through level 3.
* Autogenerated section IDs
+
These IDs are used for anchors and for the table of contents.
* *(X)* Custom ID and reference text assignment, written `[[custom-id]]`.
+
Reason: Custom IDs are not needed until cross-references exist. Add them with
cross-references.

== Paragraphs and Text Formatting

* Paragraphs
* Bold text, written `*text*`
* Italic text, written `_text_`
* Monospace text, written `` `text` ``
* A delimiter starts a span only at a word boundary.
+
This keeps `snake_case_name` unchanged.
+
This also keeps arithmetic such as `2 * 3 * 4` unchanged.
* Monospace content is literal.
+
No formatting is recognized inside a code span.
+
For example, `` `foo_bar_baz` `` keeps its underscores.
+
This differs from Asciidoctor, which substitutes inside backticks.
+
Reason: A code span exists to show text exactly as written. Reading code span
content as markup is the bug this parser was built to avoid.
* *(?)* Hard line breaks
* *(?)* Subscript and superscript

== Lists

* Unordered lists
+
The only unordered list marker is `*`.
* Ordered lists
+
The only ordered list marker is `.`.
* Description lists
+
A description item has this form:
+
----
term:: definition
----
+
The delimiter is the first `::` followed by one of these:
+
** a space
** the end of the line
+
The term must appear before the delimiter.
* `image::path[alt]` is not a description item.
+
In a block image macro, the target starts immediately after `::`.
+
In a description item, a space or the end of the line follows `::`.
+
This single rule separates block image macros from description items.
* A term can contain colons.
+
For example, `` `:date:`:: `` is read as the term `` `:date:` ``.
* A definition can continue on later lines, like a list item.
* A term can appear with no definition after the delimiter.
+
In that case, the definition starts on the following lines.
* A prose line that contains `::` followed by a space starts a description
  item.
+
There is no escape for this case yet.
+
Reason: Double colons followed by a space are rare in prose. A documented limit
is better than an escape rule that no document has needed.
* Checklists, written `[ ]`, `[x]`, or `[X]`
+
Literal bracket text at the start of a list item must be escaped. For example,
write `\[ ]`.
+
This is necessary because checklist syntax is recognized at the start of a list
item.
* A list item continues onto following lines until the next list item or the
  next block.
+
This lets long items wrap across lines.
* A list marker is a marker only in the first column, followed by a space.
+
This keeps a line that starts with `*bold*` as a paragraph.
+
This also follows from the absence of nested lists. An indented marker would
have no list level to enter.
* *(X)* Hyphen-marker unordered lists, written `-`.
+
Reason: A line that starts with `-` can be a list item, quoted prose, or prose
after an em dash. One marker avoids that ambiguity.
* *(X)* Nested lists.
+
Reason: They are not yet needed. A single list level covers all documents
written so far. Revisit this when a real document needs nesting.

== Links and Images

* Autolinks for bare `http://` and `https://` URLs
+
A URL stops before trailing sentence punctuation. Thus, a link at the end of a
sentence does not include the period.
+
Punctuation is kept when more URL text follows it.
* Link macro, written `link:url[text]`
+
`link:url[]` displays the target.
* Block image macro, written `image::path[alt text]`
+
The macro must be alone on its line.
+
The closing bracket must end the line. Otherwise, the text is ordinary prose.
* Inline image macro, written `image:path[alt text]`
* Attribute lists are positional.
* Attribute lists end at the first `]`.
* There is no way to escape a closing bracket inside an attribute list.
+
Reason: A partial escape rule that is not documented is worse than a documented
limit.
* *(?)* Autolinks for other schemes, especially `mailto:`
* *(?)* Named attributes
* *(?)* Image width and height
* *(X)* Audio and video macros.
+
Reason: There is no current use case. The target content is text-first and
image-first.

== Admonitions

* Single-paragraph admonitions with these labels:
+
** `NOTE:`
** `TIP:`
** `WARNING:`
** `IMPORTANT:`
** `CAUTION:`
* The label must match exactly.
+
The space after the colon is part of the syntax.
+
A paragraph that starts with `NOTES: ` or `Note: ` is prose.
* *(?)* Block admonitions, written with `[NOTE]` above a delimited block
+
This is the admonition form that can contain more than one paragraph.

== Blocks

* Delimited listing blocks, written `----`
* Source blocks with a language attribute, written `[source,lang]`
* Delimited STEM or math blocks, written `++++`
* Inline STEM or math, written `stem:[...]`
* STEM notation is literal, like a code span.
+
For example, `stem:[a_1 * b_2]` keeps its underscore and asterisk.
+
cl-adoc does not parse the notation. It passes the notation to the math
renderer used by the page.
* A bare `++++` block is mathematics.
+
Asciidoctor treats a bare `++++` block as passthrough.
+
In cl-adoc, write `[pass]` above `++++` to request passthrough.
+
Reason: Math is the reason this project chose AsciiDoc. Raw markup is less
common.
* `[stem]` can be written above a `++++` block.
+
It states what the bare delimiter already means.
* Inline `stem:[...]` ends at the first `]`.
+
If notation contains a closing bracket, write it in a block instead of inline.
* Blockquotes, written with the line prefix `> `
* A bare `>` separates paragraphs inside a quotation.
* The space after `>` is required.
+
A line that starts with `>text` is prose.
* *(?)* Quotation attribution, written `[quote, author, source]`
* *(X)* Sidebars, example blocks, and open blocks.
+
Reason: No current content needs them. They are straightforward to add when a
document needs them.
* *(X)* Callouts in source blocks.
+
Reason: Good callout support needs comment-syntax knowledge for each language.
That is too much complexity for a feature that can be replaced by a numbered
list below the source block.

== Tables

* *(?)* Basic `|===` delimited tables with pipe-separated cells
* *(?)* First row as header
* *(X)* Nested tables.
+
Reason: Nested tables are almost always the wrong way to present information.
If the data needs that shape, the data needs a different structure, not a
nested table.
* *(X)* Column and cell format specifiers, such as widths, spans, and
  alignment.
+
Reason: They are not yet needed. Add them when a real table needs them.

== Includes

* *(?)* Single-file include directive
* *(X)* Include by tagged region
* *(X)* Include by line range
* *(X)* Include by URI
+
Reason: These features add real complexity. No current document needs them.
The URI form also adds a network dependency to a build that should be
deterministic.

== Comments

* *(?)* Line comments, written `//`

== Substitutions

* Special character escaping in source and listing blocks
* Special character escaping in ordinary paragraph text
* Backslash escapes for inline formatting delimiters
* Passthrough blocks
+
A passthrough block is written as `[pass]` above a `++++` block.
+
The contents reach the output unchanged, including escaping.
+
This is the only construct that emits markup that cl-adoc did not generate.
For that reason, passthrough must be requested by name. It is not the default
meaning of the delimiter.
* *(X)* Custom substitution ordering per block.
+
Reason: This is an escape hatch for a problem this document set has not hit.
